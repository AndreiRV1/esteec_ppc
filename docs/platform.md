# FileGrid Platform & Observability

## What runs

`compose.yaml` starts the full stack split across three internal networks (`edge`, `backend`, `observability`) so storages are never directly reachable from outside:

- **`edge` network**: `proxy` (Caddy TLS reverse proxy, the only service with a published host port in `make up`), `frontend` (Nginx static SPA when `frontend/Dockerfile` is present, or Caddy's built-in placeholder page when absent), `backend`, `keycloak`, `grafana`, `mailpit`.
- **`backend` network**: `postgres` (PostgreSQL 18), `minio` (S3-compatible object store), `ftp` (vsftpd), `db-migrate` (Flyway), `minio-init`, `keycloak`, `backend`, `blackbox`.
- **`observability` network**: `prometheus` (scrapes `backend:8081/actuator/prometheus` and `blackbox:9115`), `blackbox` (probes PostgreSQL, MinIO, and FTP), `alertmanager` (sends alert emails to `mailpit`), `loki` + `alloy` (collects container logs from Docker and parses backend ECS JSON logs with `trace_id`), `tempo` (receives OTLP traces on `:4318`), `grafana`.

## URLs (`make up` vs `make dev`)

`FILEGRID_PUBLIC_URL` defaults to `https://localhost:8443` (`PROXY_HOST_PORT=8443`, bound to `127.0.0.1`). Caddy issues a certificate for the configured hostname from its local CA stored in the `proxy-data` volume (`proxy:/data/caddy/pki/authorities/local/root.crt`).

| Path / Service | `make up` | `make dev` |
|---|---|---|
| Web UI (or placeholder) | `https://localhost:8443/` | `https://localhost:8443/` or `http://localhost:4200` (`npm start`) |
| Backend REST API | `https://localhost:8443/api/v1` | `https://localhost:8443/api/v1` (proxied to host `:8080`) and `http://localhost:8080/api/v1` |
| OpenAPI / Swagger UI | `https://localhost:8443/swagger-ui.html` | `https://localhost:8443/swagger-ui.html` or `http://localhost:8080/swagger-ui.html` |
| Keycloak (`/auth`) | `https://localhost:8443/auth` | `https://localhost:8443/auth` and `http://localhost:8180/auth` |
| Grafana (`/grafana/`) | `https://localhost:8443/grafana/` | `https://localhost:8443/grafana/` |
| Alert inbox (`/mailpit/`) | `https://localhost:8443/mailpit/` | `https://localhost:8443/mailpit/` |
| PostgreSQL / MinIO / FTP | *internal only* | `127.0.0.1:5432`, `127.0.0.1:9000`/`:9001`, `127.0.0.1:2121` (`21100-21119`) |
| Meter simulator sink (service `simulator`, started by `make up`; `make sim`) | `http://proxy:8080/api/v1/meter-readings` (on `edge` network) | `http://proxy:8080/api/v1/meter-readings` (forwarded to host `:8080`) |

## OIDC token issuer

Keycloak runs behind `/auth` with `KC_HOSTNAME=${FILEGRID_PUBLIC_URL}/auth` and `KC_HOSTNAME_BACKCHANNEL_DYNAMIC=true`.
- Every access token has issuer **`${FILEGRID_PUBLIC_URL}/auth/realms/filegrid`** (default `https://localhost:8443/auth/realms/filegrid`) and audience **`filegrid-api`**.
- The backend validates `issuer-uri: ${FILEGRID_PUBLIC_URL}/auth/realms/filegrid` in both `make up` and `make dev`, while fetching the JWK set over internal HTTP (`http://keycloak:8080/auth/realms/filegrid/protocol/openid-connect/certs` in Docker, `http://localhost:8180/auth/realms/filegrid/protocol/openid-connect/certs` on the host in `make dev`).
- The public OIDC client `filegrid-web` (Authorization Code + PKCE) allows redirect URIs and web origins for both `${FILEGRID_PUBLIC_URL}` and `http://localhost:4200`.

## Grafana login and embedding

Grafana is served at `${FILEGRID_PUBLIC_URL}/grafana/` with its own login form disabled (`GF_AUTH_DISABLE_LOGIN_FORM=true`, `GF_AUTH_OAUTH_AUTO_LOGIN=true`):
- Browsers are redirected to Keycloak (`client_id=filegrid-grafana`).
- The `realm-roles` mapper puts Keycloak realm roles into the `roles` claim.
- Grafana checks `contains(roles[*], 'admin') && 'Admin'` with `GF_AUTH_GENERIC_OAUTH_ROLE_ATTRIBUTE_STRICT=true`: users with the `admin` realm role (such as `admin@filegrid.local`) sign in as Grafana `Admin`; users without `admin` (`client`, `employee`) are denied access.
- Same-origin iframe embedding is enabled (`GF_SECURITY_ALLOW_EMBEDDING=true`, `X-Frame-Options: SAMEORIGIN` at the proxy) so the web UI can embed panels under `/admin/monitoring`.

## Dashboards, traces and alerts

- **Dashboards** (`infra/observability/grafana/dashboards/*.json`, generated by `infra/observability/grafana/generate-dashboards.py`):
  - `filegrid-overview` (*FileGrid - Overview*): active backend replicas, request rate, error rate, p50/p95/p99 HTTP latency by category (`METER_READING`, `FAULT_RECORD`, `CONNECTION_DOCUMENTS`, `DRONE_VIDEO`), storage throughput/latency/errors by backend (`DATABASE`, `FTP`, `S3`), firing alerts, and WARN/ERROR logs linked to traces.
  - `filegrid-storage` (*FileGrid - Storage backends*): side-by-side throughput, error rate, p50/p95/p99 latency per `(category, backend, operation)`, SHA-256 integrity failures (`filegrid_storage_integrity_failures_total`), and Blackbox storage probe status.
  - `filegrid-meters` (*FileGrid - Meter readings*): pending raw backlog (`filegrid_meter_raw_pending`), oldest pending age (`filegrid_meter_raw_oldest_pending_seconds`), ingest status codes (`202` stored, `200` duplicate absorbed), processor throughput, and anomaly rate (`filegrid_meter_readings_total{quality="anomaly"}`).
- **Logs & traces**: Alloy ships container logs to Loki and extracts `trace_id` from backend ECS JSON logs; traces go to Tempo and are linked both ways with Loki in Grafana.

### Following one operation from the request to storage

Every API operation is one trace in Tempo:

```
filegrid-proxy  proxy POST /api/v1/fault-records            <- Caddy, the entry point (root span)
filegrid          http post /api/v1/fault-records           <- backend request (auth, validation)
filegrid            db record file                          <- metadata row, status UPLOADING
filegrid            storage put                             <- the storage call: filegrid.category, .backend,
                                                               .file_id, .location, .bytes
filegrid            db confirm file                         <- checksums recorded, status STORED
```

- The id is returned on every API response as **`X-Trace-Id`**, shown in the app after each upload or
  submission ("ID operație") and in every error message, and stored with the data (`stored_file.trace_id`,
  `meter_reading_raw.trace_id`). The admin request page links the racordare's submission trace.
- **Monitorizare → Urmărește o operație** (admin) opens any id in Grafana Explore. Meter messages carry
  the device's `traceparent`, so all retries of one reading share a trace (the device span is outside FileGrid).
- In Kubernetes the entry span comes from the ingress controller once its OpenTelemetry module is enabled;
  without it traces start at the backend.

### Alerts: the team is told when a business requirement is at risk

Rules in `infra/observability/prometheus/rules/filegrid-alerts.yml`, one group per row of spec table 2.1.
Every alert carries a `requirement` label naming the guarantee at risk:

| Requirement (table 2.1) | Alerts |
|---|---|
| Meter readings: none lost or duplicated | `MeterReadingsNotProcessed`, `MeterBacklogGrowing`, `MeterIngestFailing`, `MeterReadingsRejected`, `MeterIngestSilent` |
| Fault records: available immediately to dispatch | `FaultRecordsSlow`, `FaultRecordsFailing` |
| Connection documents: personal data protected, auditable | `ConnectionDocumentsFailing`, `ConnectionDocumentsAccessDenied` |
| Drone videos: transfer survives slow, unstable links | `DroneVideoUploadsFailing` |
| Every category: confirmed files kept and identical | `FileIntegrityFailure`, `StorageBackendDown`, `StorageOperationsFailing`, `StorageOperationsSlow`, `BackendDown`, `BackendInstanceDown` |

- **Notification:** Alertmanager e-mails the on-call address (`infra/observability/alertmanager/alertmanager.yml`,
  template `filegrid.tmpl`): subject `[FileGrid] Cerință în pericol: <requirement> – <alert>`, then a resolved
  mail when it clears. Locally the inbox is Mailpit (`https://localhost:8443/mailpit/`, this machine only);
  for production point `smtp_smarthost` at the company relay or add a chat webhook receiver.
- **In the app:** Monitorizare → *Alerte active* lists what is firing now (`GET /api/v1/admin/alerts`, read
  from Alertmanager), refreshed every 30 s.
- **Try it:** `docker compose stop ftp` → within about 2 minutes `StorageBackendDown` fires and the mail
  arrives; `docker compose start ftp` → resolved mail.

## Scaling the backend with Docker Compose

Because `backend` publishes no host ports, scale it directly:

```sh
docker compose up -d --scale backend=2
```

- **Load balancing**: Caddy resolves all `A` records of `backend` (`dynamic a` every 5 s, `least_conn`) and distributes requests across all replicas.
- **Metrics**: Prometheus discovers every replica via DNS service discovery (`dns_sd_configs` on `backend:8081`).
- **Resumable uploads & meter processing**: upload progress lives in PostgreSQL (`stored_file`), so any replica can handle any part; the meter processor claims batches with `FOR UPDATE SKIP LOCKED`, preventing duplicate processing across replicas.
